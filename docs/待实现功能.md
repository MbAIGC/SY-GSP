## 功能 1: GitHub Action 生成可读 Markdown 镜像

**需求**: 仓库端增加 GitHub Action,解析 `/data` 内容:笔记本 → 文件夹,笔记 → md 文件(内容转 Markdown),使 GitHub 网页可直接阅读笔记。

### 可行性: 高(推荐做)

**两条实现路径**:

| 路径 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. Action 内转换(推荐) | Action 脚本解析 `.sy`(思源块树 JSON)→ Markdown | 设备端零开销;镜像不占设备资源 | 需实现块类型→MD 映射(段落/标题/列表/代码块/表格/引用/内联样式/图片引用等,约 300-600 行转换器);复杂块(公式/挂件/嵌入块)保真度有限 |
| B. 设备端导出 | 同步时经内核 `/api/export/exportMdContent` 导出 md 一并推送 | 复用内核导出,保真度高 | 每轮 N 次导出调用;镜像进 git 历史,仓库体积翻倍;设备端负担 |

**关键设计点(路径 A)**:

1. **输出位置必须是独立分支**(如 `mirror`),严禁写回 `main` 的 `data/`——否则镜像文件会被插件视为"仅远端文件"触发删除,或进入同步范围造成污染;
2. **层级映射**: `.sy` 文件本身不含文档树层级(hpath 在内核数据库)。方案: 插件在上传时同步生成一份 `hpath 清单`(文档 id → 层级路径),Action 读取清单还原"笔记本/父文档/子文档"目录结构。清单文件放仓库根 `sy-gsp/manifest/`(插件同步范围外,Action 专属);
3. **笔记本名映射**: 读取 `data/<id>/.siyuan/conf.json` 的 `name` 作为文件夹名(该文件已同步,含 icon 可选用);
4. **资源引用**: md 内 `assets/...` 引用相对化指向仓库内 `data/assets/`;
5. **触发**: `push` + `paths: data/**`;冲突保护: 输出分支强制覆盖(force push),镜像分支不参与任何同步。

**边界声明**: 镜像定位为"在线阅读视图",不是备份——备份永远是 `.sy` 原文件;复杂块转换不完美属预期。

## 功能 2: 插件自动升级

**需求**: 插件出新版本后自动升级,免除各端手动更新。

### 可行性: 检查+提醒=高;全自动安装=中低(风险高)

| 层级 | 做法 | 评估 |
|---|---|---|
| L1 检查+提醒(推荐先行) | 启动及每日一次调 GitHub `releases/latest` 对比 `plugin.json` 版本 → 顶栏角标+菜单项"有新版本 vX → vY",点击打开 release 页 | 无风险;公开仓库无需 token(低频调用避开限流) |
| L2 一键升级 | 插件内下载 release 资产 → 覆盖 `data/storage/petal/SY-GSP/` 安装目录 → 提示重启思源 | 需处理: 覆盖自身运行文件、失败回滚(先备份旧版目录)、平台差异(安卓文件权限) |
| L3 全自动静默升级 | L2 + 免确认定时执行 | 变砖风险最高: 升级失败后插件无法自愈,必须用户手动修 |

**建议**: 本期实现 L1;L2 作为实验特性(设置内默认关闭的开关);L3 不做。

**注意**: 思源市场渠道安装的插件由思源客户端负责更新,本功能主要服务"从 GitHub 手动安装"的场景(即当前多端实测场景)。

## 功能 3: 支持二级目录

**需求**: 仓库与同步结构支持目录层级(如 `data/<笔记本>/<一级文档>/<子文档>.sy`),不再全部平铺在笔记本根。

### 可行性: 中偏高,工程量大(建议独立迭代)

**现状**: 设备侧思源文档**物理平铺**(`data/<nb>/<docId>.sy`),父子关系只存在于内核数据库(hpath)。当前同步按路径平铺同步,层级信息丢失(与功能 1 同源)。

**方案(虚拟层级映射)**: 设备侧保持平铺不动(思源内核约束,文件路径不可改写),**仓库侧按 hpath 映射出目录层级**:

1. 上传时经内核 `/api/filetree/getHPathByID` 获取每个文档的 hpath(结果缓存进 BASE 元数据,避免每轮全量调用);
2. 仓库路径规则: `data/<nb>/<一级文档目录>/<子文档>.sy`(固定两层,更深层级按 docId 平铺,控制复杂度);
3. **同步体系适配**(工程量主体):
   - BASE/manifest 按新路径重建: 提供一次性"路径迁移"机制,旧路径映射新路径,**避免全库删除+重传的风暴**;
   - **移动/重命名语义**: 文档在树中移动 = 仓库路径变化,必须实现"移动"判定(结合 hpath 清单与墓碑,见功能 4),否则每次移动都是删除+新建,历史断裂;
   - 忽略规则按新路径适配;冲突中心的路径展示与友好名(笔记本/文档)适配。

**风险**: 路径带标题后,重命名/移动的处理是全部复杂度所在;先出独立设计文档评审,再动工。

## 功能 4: 强制删除笔记本及笔记(墓碑机制)——防"删除被复活"

**需求**: 一端强制删除笔记本/笔记后,其他端的同步不得将其复活;同时提供明确的"强制删除"操作入口。

### 可行性: 高(建议优先实施——属数据安全补强)

**现状根因**(复活的三条路径):

1. 对端在删除发生**之前**抓取的远端状态 → 该端后续同步把文件判为"本地新建/本地修改"推回(无 BASE 或 BASE 陈旧时尤甚);
2. 内核对已注册笔记本自动重建 conf.json(本轮 conf.json 冲突即此机制的体现);
3. 重建残留清理只覆盖"内核列表之外的目录",对已注册笔记本的强制删除没有统一出口。

**方案: 墓碑(tombstone)机制**

1. **墓碑文件**: 仓库根 `sy-gsp/tombstones.json`(位于 `data/` 之外,不进内容同步;插件加入固定 ignore),结构 `{ "<path>": {"at": 删除时间, "by": 设备名} }`;
2. **写入时机**: 凡执行"远端删除"(deletionsRemote)或"本地清理"(deletionsLocal, 含 removeNotebook 注销)时,同步写入墓碑;多端并发写按 **union + 同路径取最新时间** 合并(该文件每轮全量读取重写,冲突面小);
3. **生效时机**: 各端规划前读取墓碑——本地存在、且墓碑记录晚于本端 BASE 的路径 → 判"已删除": 本地执行清理(含 removeNotebook 注销),**绝不复活上传**;
4. **强制删除入口**: 重建面板/设置增加"强制删除笔记本"列表(按内核笔记本列出),勾选后写墓碑 + 立即执行两端删除;UI 二次确认与现有重建一致;
5. **生命周期**: 墓碑保留 30 天后由引擎清理(避免无限膨胀);期间若同名路径在远端重新出现且内容晚于墓碑 → 视为重新创建,墓碑失效(需用户新建同名笔记本的场景);
6. **多端要求**: 需各端同步更新(旧端仍可能复活,直至其升级)。

**与功能 3 的关系**: 墓碑按"路径"记录,二级目录上线后路径规则变化需兼容(建议功能 4 先行落地,功能 3 设计时继承)。

## 建议实施顺序

| 优先级 | 功能 | 理由 |
|---|---|---|
| 1 | 功能 4 墓碑/强制删除 | 数据安全补强,消除"删除被复活"这一多端同步的经典缺陷 |
| 2 | 功能 1 Action 镜像 | 独立性强、零设备开销、无同步体系风险,直接提升使用体验 |
| 3 | 功能 2 L1 检查更新 | 低风险高频价值;多端升级不同步正是本轮多个问题的放大器 |
| 4 | 功能 3 二级目录 | 工程量最大,依赖功能 4 的墓碑与移动语义,需先出独立设计评审 |

## 风险与验证要求(实施时统一遵循)

- 每项均需先补"删除/复活/迁移"方向的收敛性测试(延续 tests/convergence.test.mjs 的 T1/T2 模式);
- 涉及破坏性操作(强制删除、自动升级)必须有: 预览确认 + 备份 + 回退路径;
- 真机验证矩阵: NAS/安卓/网页端三端组合至少各一轮。
