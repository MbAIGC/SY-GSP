## 当前版本复核结论

### 已确认的基础能力

- GitHub Git Data API 提交使用引用 CAS，并在确认后才更新 BASE；远端读取不完整、推送未确认和大文件跳过均不会伪报成功。
- 普通同步使用 BASE/本地/远端三方规划；无法安全判定的修改进入冲突中心，不自动覆盖。
- 同步重建支持双向镜像、二次确认和“以本地为准”后的远端回读校验；无注册或已关闭的笔记本残留会走内核 `removeNotebook` 清理。
- 原生 `.sy` 下载会写入、刷新文件树并在新建时打开笔记本；笔记本 `conf.json` 以 `name`、`icon` 字段级语义同步，设备侧状态保留本地。

### 本轮验证

```text
npm test：240/240 通过
npm run smoke：12/12 通过
```

### 审查发现与后续约束

1. 当前没有确认的 P0/P1 数据一致性缺陷；早期审查中关于“远端分支 404 被当空仓库”“新设备以首提交作引导基准”“CAS 漂移错误推进 BASE”等问题，在当前版本已经有对应保护或修复，不能重复按现状报告。
2. 仍需补强的中风险测试盲区包括：自定义忽略目录与远端删除语义不一致、下载/删除前的快照后并发修改、Markdown canonical 表示的多端往返，以及异常响应正文和边界 API 的真实环境验证。
3. `src/local/notebook-conf.js` 的顶部说明称“只有 name”，实际实现还同步 `icon`。这是文档注释不一致，应在后续相关改动中修正，避免设计误判。
4. 自动化测试主要使用假内核与假 GitHub Provider。新增破坏性功能前，必须增加真实 GitHub 测试仓库和 Android/桌面/网页端真机验收矩阵，不能只依赖单元测试。
5. 下列功能中的控制面元数据不能按普通 `data/` 文件处理。需要建立受引擎明确识别的控制面命名空间和专用读写通道，避免“工作空间范围”把元数据当成普通远端文件下载或删除。
6. 当前 `deletionsLocal` 轮次通常没有远端提交点；任何共享删除协议都必须单独处理本地删除产生的墓碑传播，不能只挂接 `deletionsRemote`。
7. 当前本地残留笔记本清理中，备份失败会被记录后继续注销。强制删除功能应把“备份成功或明确用户选择跳过”作为破坏性删除前置条件，不能静默吞掉备份失败。

## 总体架构原则

```text
插件原始数据面：本地 data/** ↔ GitHub data/** 或 GitHub 目录X/data/**
  思源原生 .sy、笔记本 conf.json、资源文件
  由插件同步，目标前缀由用户设置；目录X 内部保持完整 data 结构

Action 阅读数据面：GitHub 已存在的指定 data/**
  Action 读取 conf.json 和 .sy，在仓库根生成笔记本名称/笔记名称 Markdown 目录
  不回写插件原始 data/**，也不参与插件同步规划

控制面：.sy-gsp/**
  文档层级索引、强制删除墓碑、设备确认信息
  不作为普通文件进入三方合并；由专用服务读取、合并和原子提交

展示面：GitHub mirror 分支或 GitHub Pages
  Markdown 和可读目录仅用于浏览；Action 仅读取 main 的 data/**，绝不写回原始数据路径
```

控制面必须列入固定忽略规则，同时由专用代码显式读写。控制面与本轮数据面变更应尽量在同一个 Git 提交树中更新，以保持原子性。

## 功能一：GitHub Action 生成 Markdown 阅读镜像

### 目标

当 `main` 已有的 `data/**` 思源原生数据发生变化时，自动产生可浏览的结构：

```text
笔记本名称/
  一级文档/
    二级文档.md
```

笔记本名称来自 `data/<notebookId>/.siyuan/conf.json` 的 `name`；Markdown 文件名来自文档标题。原始 `.sy` 文件仍保留在 `main`，不被转换结果替代。

### 可行性与推荐方案

可行，推荐在 GitHub Action 内生成并发布到独立 `mirror` 分支，或从该分支部署 GitHub Pages。

不建议让 Action 回写 `main`：若 Markdown 与 `data/` 混在同一同步分支，插件会把它们当作远端普通文件，带来下载、删除和冲突污染。

Action 的职责：

1. 监听 `main` 已存在的 `data/**` 和可选 catalog 变更；
2. 直接读取 `data/<笔记本ID>/.siyuan/conf.json` 生成笔记本显示名；
3. 直接读取 `data/<笔记本ID>/*.sy` 解析笔记内容；存在 catalog 时再补充一级/二级父子关系；
4. 将 `.sy` 块树转换为 Markdown；
5. 生成稳定、转义后的路径和一个索引页；
6. 只更新 `mirror` 分支，提交信息标注来源提交 SHA。

### 关键难点和解决方案

- `.sy` 的物理路径与思源文档层级不是同一概念，不能从文件名可靠推导父子关系。
  - 解决：第一期 Action 直接解析 GitHub 已存在的 `data/**` 和 `conf.json`，按笔记本/笔记生成稳定 Markdown 文件名；若仓库存在可选 catalog，则用于补充父子层级，不存在时不阻断基础镜像。
- 标题重名、非法文件名和改名会造成路径碰撞。
  - 解决：文件名使用“清洗标题--短文档 ID.md”；显示标题保留在正文首行。路径稳定性优先于纯标题美观。
- 复杂块、嵌入块、公式、数据库和挂件难以 100% 还原 Markdown。
  - 解决：第一期仅承诺段落、标题、列表、引用、代码、表格、图片链接和常用行内格式；无法表达的块生成明确占位说明，并保留原始块 ID 链接。镜像定位为阅读视图，不是可逆导入格式。
- 资源路径需要指向原始分支或镜像分支的资源副本。
  - 解决：镜像使用 `raw.githubusercontent.com/<repo>/<main-sha>/data/assets/...` 的固定来源 SHA，避免镜像分支复制大资源导致仓库膨胀。

### 落地步骤

1. 定义 `.sy-gsp/catalog.v1.json` 的 schema、版本和升级策略。
2. 插件只在文档树有变化时刷新目录索引，使用内核 SQL/文档树 API 获取 `docId`、标题、父级和 hpath。
3. 用 Node.js 写独立转换器，先覆盖常用块类型并建立 `.sy` fixture 测试集。
4. 增加 `.github/workflows/render-mirror.yml`，最小权限为 `contents: write`，并使用并发组取消过时构建。
5. 生成独立镜像分支并用固定 SHA 回链原始提交。
6. 在真实仓库中验证中文标题、重名、资源、空笔记本、改名和复杂块降级表现。

### 验收标准

- Action 不修改 `main` 的原始 `data/**`；
- 同一个 source SHA 重跑生成结果字节稳定；
- 标题改名、文档移动和资源引用均不产生路径碰撞；
- 原始 `.sy` 不可解析时，Action 失败并保留上一份镜像，不产出半成品。

## 功能二：插件自动升级

### 目标

降低各端版本不一致带来的兼容问题，但不能在更新失败时破坏现有可用插件。

### 可行性与推荐分级

| 阶段 | 功能 | 建议 |
|---|---|---|
| U1 | 检查并提示新版本 | 必做，低风险 |
| U2 | 用户点击后下载、校验和安装 | 可做，作为实验开关，默认关闭 |
| U3 | 静默自动安装 | 不做 |

### U1：更新检查

1. 启动后延迟检查，并以 24 小时为最短间隔；
2. 读取 GitHub Release 的稳定版标签，与 `plugin.json` 当前版本使用语义化版本比较；
3. 显示“发现 vX，可查看更新”的菜单项，点击打开 Release 页面；
4. 请求失败、限流或离线仅记录日志，不影响同步；
5. 支持“跳过此版本”和“关闭检查”设置。

### U2：一键升级的前置条件

仅面向从 GitHub Release 手动安装的插件，不接管思源市场的升级渠道。发布包必须包含：

```text
release.zip
release.sha256
release-manifest.json
```

`release-manifest.json` 至少含版本、文件列表、每个文件 SHA-256、最低兼容思源版本和发布包 SHA-256。

安装流程：

1. 用户点击“下载并安装”；
2. 下载到临时目录，校验 Release 资源 SHA-256 和文件清单；
3. 校验版本可升级、无同步任务运行、目标目录可写；
4. 备份当前插件目录；
5. 解压到临时目录并再次校验；
6. 使用“目录替换或逐文件原子替换”安装；
7. 写入安装结果，提示用户重启或重新加载插件；
8. 任一步失败时恢复备份并给出可见错误。

Android 的文件权限、插件运行期自覆盖和思源实际插件目录行为必须先在真机验证。若内核未提供可靠安装 API，U2 停留在“下载、校验、打开安装目录”的辅助模式，不伪造一键安装成功。

### 验收标准

- U1 不增加同步 API 调用，不持有用户 GitHub Token；
- U2 失败后旧版本文件仍完整可加载；
- 不自动跨越预发布版、降级或不兼容主版本；
- Android、桌面和网页端各自验证更新检查，安装能力按平台单独启用。

## 功能三：GitHub 端自定义二级目录

### 目标

当前插件把同步数据写在 GitHub 仓库根目录：

```text
repo/
└── data/
```

新增一个用户可配置的“GitHub 同步目录名”，例如填写 `目录X` 后，插件写入：

```text
repo/
└── 目录X/
    └── data/
        ├── <笔记本ID>/
        ├── assets/
        └── 其他现有同步数据
```

这里的“二级目录”是 GitHub 仓库根目录下增加一个容器目录，不是把笔记标题改成 GitHub 文件夹，也不是改变思源本地 `.sy` 文件布局。笔记本和笔记仍保持现有 `data/<笔记本ID>/...` 内部结构。

### 推荐方案：统一远端路径前缀

- 本地路径完全不变，仍扫描和读写 `data/**`；
- GitHub 路径由 `remoteRoot + localPath` 生成：
  - `remoteRoot = ""` 时保持兼容，远端为 `data/**`；
  - `remoteRoot = "目录X"` 时远端为 `目录X/data/**`；
- 仅在 Provider/同步引擎的远端路径边界做加前缀和去前缀，内部 planner、内容适配器、Android `putFile`、manifest 和 BASE 继续使用本地标准路径；
- 用户只能设置相对目录名，禁止 `..`、绝对路径、空路径段、`.`、反斜杠和控制字符；统一使用 `/` 分隔；
- 目录名变更属于远端路径迁移，必须先只读预览“旧前缀文件数、目标前缀文件数和预计删除/上传数量”，确认后通过 GitHub 单次原子树提交迁移。

### 迁移与兼容

1. 新设置默认空字符串，现有用户无需迁移，继续使用根目录 `data/`；
2. 设置为 `目录X` 后，首轮只允许“迁移向导”执行，不能让普通同步把旧 `data/` 判成删除、新 `目录X/data/` 判成新增；
3. 迁移提交完成后，BASE、远端 HEAD 和本地 manifest 必须以新远端路径集合重新确认；
4. 同步重建、冲突路径、删除守卫和诊断面板都要显示完整 GitHub 路径，但本地落地仍去掉 `目录X/` 前缀；
5. 更换或清空目录名必须同样走迁移预览和二次确认，防止误删另一套目录；
6. 旧版本客户端不认识自定义前缀时可能继续操作根目录 `data/`，因此启用前必须提示“所有设备升级到支持前缀的版本”，并在协议版本不匹配时暂停普通同步。

### 验收标准

- 空前缀的现有仓库行为完全不变；
- 设置 `目录X` 后，GitHub 只出现 `目录X/data/**` 原始同步数据，不出现根目录 `data/**` 的新副本；
- Android 下载 `目录X/data/**` 时本地仍落到 `data/**`，不把 `目录X` 写进思源数据路径；
- 迁移中断、CAS 竞争或网络失败不会报告成功，也不会同时删除旧目录和新目录；
- Action 功能仍独立读取它被配置的原始 `data/**`，不把 `目录X` 前缀误当笔记本名称或 Markdown 目录。

## 功能四：强制删除笔记本及笔记，防止被另一端复活

### 问题定义

普通删除遵循三方同步语义：远端有独立修改时会进入冲突，避免意外丢失数据。强制删除是不同语义：用户明确声明某个笔记本或文档已永久废弃，旧设备即便仍存有副本，也不得在下一轮上传将其复活。

### 可行性与核心更正

可行，但不能只用“路径 + 30 天过期”的墓碑方案。路径会因改名/目录展示变化而改变，而离线超过 30 天的旧设备会在墓碑过期后重新上传旧内容。

墓碑必须基于稳定身份，并保留到所有已知设备确认或由用户显式重新创建：

```json
{
  "schemaVersion": 1,
  "tombstones": [
    {
      "kind": "document",
      "notebookId": "20260101010101-abc",
      "docId": "20260101010102-def",
      "deletedAt": "2026-09-10T12:00:00.000Z",
      "deletedBy": "设备 A",
      "deleteCommit": "<git sha>",
      "generation": 1
    }
  ]
}
```

笔记本墓碑使用 `kind: "notebook" + notebookId`，并隐含其所有文档；文档墓碑以 `notebookId + docId` 为键。新建文档使用新的思源文档 ID，不复用已删除 ID；同 ID 的重新创建必须要求用户显式“解除删除”，并产生更高 generation。

### 数据与执行流程

1. 建立 `.sy-gsp/tombstones.v1.json` 专用控制面文件，普通同步扫描和删除规划均忽略它；
2. 每轮同步在读取数据面前读取墓碑，并按 `kind/id/generation` 合并；同一删除对象选择更高 generation，再以删除提交/时间作为稳定并列规则；
3. 规划前先应用墓碑：
   - 本地存在但已被墓碑覆盖：不允许上传，进入本地清理队列；
   - 远端存在但已被墓碑覆盖：不允许下载，进入远端删除队列；
   - 两端均存在：墓碑优先于普通文件三方合并；
4. 用户从笔记本列表或文档树选择“强制删除”，弹窗显示影响范围、文件数、备份位置和不可逆提示；
5. 提交中原子包含“数据删除 + 墓碑新增/更新”。GitHub CAS 失败时两者都不确认；
6. 本地删除笔记本使用内核 `removeNotebook`，文档删除使用内核支持的文档删除 API；仅在 API 不可用时，才按现有受控文件删除回退，并报告降级；
7. 删除执行前创建本地隔离备份。恢复不是自动撤销：需要显式“从备份恢复为新对象”，避免旧 ID 违反墓碑。

### 设备确认与生命周期

- 每个支持墓碑的设备在成功同步后更新 `.sy-gsp/device-acks.v1.json` 的已见墓碑 generation；
- 默认不自动删除墓碑；仅当所有仍活跃设备均确认，且超过保留期后，才在用户明确维护操作中清理；
- 对于无法确认的离线设备，墓碑保留。旧版本插件不能理解墓碑，因此升级提示应明确显示“旧客户端可能复活已删除内容”。

### 实施阶段

1. 先做墓碑 schema、专用读取合并、规划拦截和收敛测试；暂不开放 UI；
2. 实现文档强制删除，验证同一文档在旧设备离线、恢复在线后的不复活；
3. 实现笔记本强制删除和内核级注销；
4. 加入批量 UI、备份浏览和设备确认状态；
5. 最后实现受确认约束的墓碑维护工具。

### 验收标准

- 删除端、在线对端和离线旧对端三方交替同步后，删除对象不复活；
- CAS 竞争、网络失败和内核删除失败均不报告成功；
- 强制删除不会误作用于同名但不同 ID 的文档；
- 每一类删除均有预览、二次确认、备份位置和可追踪日志。

## 推荐实施顺序

设计依赖和交付顺序不完全相同。应先推动各设备升级，再上线会改变删除协议的功能；二级目录虽然是 Markdown 镜像的重要输入，但必须在删除身份协议稳定后实施。

| 顺序 | 工作项 | 原因 |
|---|---|---|
| 0 | 建立控制面命名空间、版本号与 schema 测试基座 | catalog、墓碑、设备确认都依赖此边界 |
| 1 | 功能二 U1：更新检查与提醒 | 利用现有 Release 契约，低风险推动各端升级；U2/U3 不进入本期排期 |
| 2 | 功能四第一阶段：专用墓碑通道、规划拦截和文档强制删除 | 先解决“删除被复活”的数据安全问题，并验证离线旧端场景 |
| 3 | 功能四第二阶段：笔记本强制删除、设备确认和维护 UI | 在文档删除收敛与内核 API 验证后扩大破坏性范围 |
| 4 | 功能一：Action Markdown 镜像 | 直接解析 GitHub 已存在的 data/**；与插件自定义同步前缀独立配置 |
| 5 | 功能三：GitHub 端自定义二级目录 | 仅增加统一远端路径前缀，保持 data 内部结构和本地原生路径不变 |

## 通用测试与发布门槛
