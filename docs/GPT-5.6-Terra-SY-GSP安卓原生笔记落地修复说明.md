# SY-GSP 安卓原生笔记落地修复说明

## 问题

网页端创建文档并同步后，Android 端同步日志显示成功，但本地只出现若干已关闭的笔记本，没有可见笔记文档。

两端配置确认使用的是「思源笔记」原生格式，不是 Markdown。原有落地流程对远端 `.sy` 文件只调用 `/api/file/putFile`，随后统一刷新文件树；刷新失败还会被忽略。Android 端可能因此只识别到数据目录和笔记本，未完成文档树登记。

## 修复

原生 `.sy` 文档下载现在按以下顺序执行：

1. 从 `data/<笔记本 ID>/...` 路径解析笔记本 ID；
2. 调用 `/api/file/putFile` 写入原生 `.sy` 文件；
3. 调用 `/api/filetree/refreshFiletree` 让内核重新扫描文档文件；
4. 最后调用 `/api/notebook/openNotebook` 加载已经存在的笔记本。

打开动作必须在文件写入和文件树刷新之后执行。若先打开一个尚未写入文档的笔记本，Android 端可能只保留关闭笔记本目录，后续刷新也不会建立预期的文档树节点。

刷新失败会直接上抛，当前同步不会更新 BASE 或报告成功，日志中会保留具体错误。

资源和其他普通文件仍使用原有直接写入路径，不会额外调用笔记本接口。

## 验证

新增测试覆盖：

- 原生 `.sy` 文件的打开笔记本、写入、刷新顺序；
- 刷新文件树失败时错误可见；
- 普通资源文件不调用打开笔记本接口。

## 重建场景

如果 Android 本地已经存在 `.sy` 文件，但文档树没有登记，普通比较会显示“本地与远端数量相同、差异 0”，因此不会重新写入。现在在「同步重建 → 以远端为准」中，即使哈希相同也会重新落地远端文件，用于触发 Android 内核重新建立文档树；普通自动同步仍会跳过内容相同的文件。

Android 真机仍需重新加载最新插件后实际验证，重点观察同步重建日志中是否出现下载数量，以及目标笔记本内是否出现对应文档。
