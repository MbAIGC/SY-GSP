# 多端同步与配置同步系列修复总结(2026-09-06)

> 承接 [2026-09-05-同步收敛修复总结.md](./2026-09-05-同步收敛修复总结.md),汇总其未覆盖的后续修复轮次。
> 全部改动已在真机(NAS/安卓/网页端)多轮实测验证;最终测试 240/240、构建与冒烟 12/12 通过。

## 一、多端同步风暴:根因定位与根治

**现象**:一台设备每秒发起 1~2 次完整同步(内核上下文序号飙升至 574),远端每秒一条 `sync: create 0, update 2` 提交;另一台设备 CAS 重试永远抢不到写入窗口,同步队列疯狂增长。

**根因(三层机制叠加,缺一不成风暴)**:

1. **写的来源(本质):conf.json/文档表示漂移**。两台设备的内核会互相改写对方的 conf.json(名称/图标/设备状态以各自内存为准),每一轮同步都制造出新的"真实差异"并推送——同步永远有活干、永远不收敛,大量写入由此而来;
2. **互相顶掉(竞争):CAS 竞争 + 退避重试**。两台设备同时持有"待推内容"时,各自推送均撞 CAS → 退避 1/3/9 秒重规划 → 再推 → 再撞,四轮重试内两端交替覆盖,表现为"远端一直在变";
3. **风暴化(放大器):自动同步间隔单位错配**。设置 UI 单位为"秒",代码按毫秒读取——600 秒被当成 600 毫秒,触发频率提升 1000 倍,把慢性乒乓变成急性风暴。

**修复(逐层对应)**:

| 层 | 修复 |
|---|---|
| 写的来源 | conf.json 规范化 `{name, icon}` + 下载经内核 setNotebookConf 应用(见第三节)——假修改不再被制造 |
| 互相顶掉 | 空图标不覆盖非空 + 字段级合并——重规划后收敛而非对撞 |
| 触发频率 | 间隔按秒计算 + 30s 下限(兼容旧毫秒值)+ 队列积压保险丝 + 手动暂停开关 |

**防护三件套**(确保任何未来异常不再拖垮客户端):队列积压保险丝(待执行 ≥20 丢弃留痕)、自动同步间隔下限 30s、菜单手动暂停开关(一键止血)。

## 二、暂停同步开关:功能与两个隐藏缺陷

新增菜单"暂停同步"(自注册 `iconSyncPause` 图标,思源内置无对应图标)。手动暂停为**权威状态**:

- 暂停期间自动同步完全停止(手动同步不受影响),顶栏图标显示橙色圆点角标,悬停提示"同步已暂停";
- 恢复路径(同步完成/冲突处理/弹窗关闭等)统一经由 `_restartAutoSyncIfConfigured`,**不得绕过手动暂停**——此前"重建/同步完成后定时器不恢复"与"手动暂停被其他路径绕过重启"两个缺陷均源于恢复逻辑分散,已统一;
- 冲突页与暂停开关文案区分:冲突项为"处理冲突(自动同步已暂停)",开关项为"暂停同步 / 恢复同步(当前已暂停)",避免混淆。

**实证缺陷回溯**:开关标签曾恒显示"恢复同步(当前已暂停)"——根因是 `isAutoSyncPaused` 以函数对象传入菜单构建(函数恒真),布尔/函数混淆导致标签不随状态变化;已改为传布尔值并新增菜单构建回归测试(tests/menu.test.mjs)。

## 三、conf.json 同步语义:从"整文件"到"字段级白名单"

**演进过程**(实测驱动,最终定稿):

1. 初版:整文件同步 → 内核高频重写 conf.json(sort/closed 等设备状态)导致反复冲突;
2. 收窄:规范化仅保留 `name` → 冲突消失,但用户反馈图标也需同步;
3. **定稿**:规范化 = `{name, icon}`,即**名称与图标参与同步,sort/closed 等设备状态差异视为文件一致**。

**四条配套规则**:

| 规则 | 说明 |
|---|---|
| 下载 = 字段级合并 | 名称/图标取远端,设备状态保留本地;本地缺失恢复远端全量(新设备/重建) |
| 下载应用 = setNotebookConf | 合并结果经内核 API 应用(内存+磁盘+UI 同时生效),整批下载完成后延后执行(等内核注册笔记本);API 失败回退写盘 |
| 上传 = 规范化 + 防抹除 | 上传内容为规范化形式;本地 icon 为空而远端非空(另一端设置过)时采用远端 icon——**空 icon 永不覆盖非空** |
| 规划守卫 | 本地丢失 BASE 中存在的 icon 且名称未变(内核抹除痕迹)→ 从远端恢复,不产生上传 |

> 说明:icon 曾一度"同步失败",根因是 conf.json 写盘后运行中的内核不读盘(内存态改写回磁盘),必须经内核 API 应用;另有一处诊断日志解析层级错误(getNotebookConf 响应配置在 `conf` 字段下)造成"icon 为空"的误读,均已修复。

**内核行为适配(实证)**:部分端思源内核对**不存在的文件**,`getFile` 返回 HTTP 200 + JSON 错误信封(`{"code":404,"msg":"file does not exist",...}`)而非失败响应。`_readLocalBytes` 统一识别信封并按"文件不存在"处理——此前新笔记本首次同步必然触发"同步期间本地新建了同名文件"假冲突,即源于此。

## 四、同步重建:残留清理的三轮演进

**用户实证场景**:网页端以本地为准重建后,远端多出的笔记本目录始终删不掉;安卓端以远程为准重建后,本地残留文件也清理不干净。

**根因与修复**:

1. **"本地全貌"定义修正**:磁盘上存在不在内核笔记本列表里的 `data/<id>/` 残留(同步只落盘、内核未注册),按磁盘扫描比对会被判"未变化"——重建既不删远端也不清本地,且残留随 BASE 写入后永久"隐身"。修正:重建以**内核笔记本列表**为本地全貌,残留目录整体清理;
2. **已关闭笔记本纳入**:思源 `lsNotebooks` 会返回已关闭的笔记本,仅"不在列表"判定对它们落空。修正:列表中标记 closed 的笔记本同样按残留清理(预览警告框显式列出);
3. **绕过忽略规则**:残留目录内可能只有被忽略文件(如 `.siyuan/sort.json`),对规划器完全隐身,路径级删除永远清不掉。修正:残留目录基于**原始目录树**整体清理(远端树删除 + 本地内核枚举清理);
4. **内核级注销**:文件级删除在安卓等端会被内核按内存状态重建(实证"删除失败")。修正:残留笔记本统一走内核 `removeNotebook`(备份 → 注销,注册/索引/数据一并删除),失败回退逐文件删除;
5. **防误伤**:残留判定仅识别思源笔记本 id 形态(14 位数字-字母数字)的目录,`data/storage`、`data/.siyuan` 等工作区目录绝不误清(实证曾误删其他插件配置,已修复并回归测试);预览页显式列出待清理残留。

## 五、新笔记本首次同步:假冲突修复

新笔记本在远端创建后,本端同步时分两步:`.sy` 文档先落地 → **思源内核立刻自动注册笔记本并生成 `.siyuan/conf.json`** → 轮到下载 conf.json 时被 M5 守卫误判"同步期间本地新建了同名文件"而中止。

修复:conf.json 的下载( create/update )均跳过 M5 拦截——其落地为非破坏性字段级合并,内核抢先创建的文件正好被合并收编。普通 `.sy` 文档的 M5 保护不变。

- **冲突中心**:批量决策按钮上移至摘要行下方(不再被长列表遮挡),底部仅留"稍后处理";高度 72vh;conf.json 类冲突不再出现;

- **设置**:设备名称置于设置页首项,首次运行生成持久化默认名;
- **README**:新增"已知限制"章节。
