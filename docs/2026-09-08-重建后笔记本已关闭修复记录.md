# 重建后笔记本全部「已关闭」修复记录

> 日期:2026-09-08
> 现象:安卓端以远端为准执行同步重建后,同步落地的笔记本全部处于「已关闭」状态(需手动逐个打开);此前 NAS 日志中新同步笔记本内核回读 `closed:true` 同源。

## 一、根因

1. `closed` 是笔记本 conf.json 的**设备本地状态**,按既定同步语义不上传(远端 conf.json 仅含 `{name, icon}`),因此远端无法纠正它;
2. 思源内核对磁盘上新出现/未注册的笔记本目录,默认按「已关闭」注册(即当年「安卓 .sy 只写盘不显示」问题的同一内核行为);
3. 插件侧唯一打开入口在 `ContentAdapter.writeFileBlob`:.sy 文件以 `op === "create"` 落地时调用 `openNotebook`;
4. **重建(以远端为准)路径的下载 `op` 几乎全为 `update`**——本地已有同名文件(切换空间前后本地 `data/**` 路径不变,旧根同步过的文件仍在)→ 强制方向按「本地已有 ? update : create」判定 → `openNotebook` 一次都不会调 → 笔记本停留于内核默认的关闭态。

数据本身完整,仅呈现状态错误。

## 二、修复

`SyncEngine._applyLocalChanges` 尾部新增**落地收口**:整批下载/删本、conf 应用与 `refreshFiletree` 完成后,汇总本轮落过文件的笔记本(conf 应用队列 + 下载路径中形如思源笔记本 id 的段),逐个 `getNotebookConf` 回查,**仅对 `closed === true` 者**调用 `openNotebook` 补打开并记运行日志。

- 收口位置遵守安卓修复教训(refresh 在前、open 在后);
- 幂等且无视图切换副作用:已打开的笔记本不触发;回读/打开失败不阻断同步(数据完整,可手动打开)。

## 三、验证

- 配对测试(convergence):模拟内核将笔记本注册为已关闭 → 重建(本地已有同名文件,op 全 update)→ 收口必须打开;第二轮(非关闭态)不再重复触发 openNotebook;
- 假内核(makeFakeKernel)增加开闭状态模拟(`__closedNotebooks`/`__openedNotebooks`/`openNotebook`/`getNotebookConf`);
- 全量 verify:test 307/307 + build + smoke 12/12。
