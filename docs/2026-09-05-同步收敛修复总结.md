# 同步收敛修复总结(2026-09-05)

> 依据:[SY-GSP代码审查与修复计划-GLM-5.3-Flash.md](../SY-GSP代码审查与修复计划-GLM-5.3-Flash.md) 审查结论,按阶段 0–2 落地。
> 目标:解决"冲突反复出现、多轮修复无法收敛"的根因,而不是继续逐症状修补冲突处理 UI。

## 一、问题与根因

1. **Markdown 往返不幂等(根因 A,冲突反复的主因)**:思源 md 导入/导出非恒等变换(块 ID、IAL、格式规范化),下载导入后再次导出的内容与远端不一致 → 每轮被判"本地已修改"重新上传 → 两台设备互相制造假修改 → 冲突永不收敛。
2. **new/new 时间静默裁决(根因 B)**:`sync-planner` 对双方同路径不同内容用 mtime 与远端 commit 时间 ±2000ms 裁决,设备时钟偏差远大于 2s,且远端时间是整条 commit 的时间——会静默选边覆盖用户数据。
3. **决策闭环缺失(根因 C)**:用户冲突决策(keep_local/keep_remote)交给引擎重规划后无任何环节验证是否真正生效;新一轮冲突集 `superseded` 旧集时旧决策被清空;`resolved`(用户已编辑)决策被忽略。
4. 若干一致性缺口:M5 守卫对快照缺失路径放行、delete_local 无枚举异常守卫(与 delete_remote 不对称)、合并结果先写本地后推送(推送失败时合并产物被下轮误判为"本地新修改")、批次预算口径不一致、分支名未编码等。

## 二、解决思路与落实情况

### 阶段 0:收敛性验收(新增 `tests/convergence.test.mjs`)

- **T1 单端收敛**:混合全部变更类型(上/下/删远/删本)一轮同步后,第二轮必须 0 操作 0 冲突。
- **T2 双端收敛**:A 推送 → B 下载收敛 → B 第二轮零操作。
- **T1(markdown 全链路)**:两台设备交替同步,漂移修正后双向收敛。

### 阶段 1(P0):消灭"自造修改"

| 修复 | 位置 | 说明 |
|---|---|---|
| markdown 回读校验 + 同轮修正推送 | `src/sync/sync-engine.js`(`_applyLocalChanges` 漂移检测 + `_applyCanonicalCorrections`) | 下载导入后回读 canonical 表示,与远端树 sha 不一致时,同轮把回读内容补推为修正提交并以此推进 BASE;下一轮即收敛,不把假修改留给用户 |
| 合并结果先推后写 | `sync-engine.js`(`_runMerges` 暂存 `plan.mergedWrites` + `_writeMergedResults`) | 推送确认后才写本地;推送失败时本地保持合并前内容,重规划不会把合并产物误判为"本地新修改" |
| new/new 裁决收紧 | `src/sync/sync-planner.js` | 阈值 2s → 30s(`newFileTimeThresholdMs`,可配置);首同步双方均有内容时引擎传 `allowTimeArbitration: false`,一律进冲突中心批量决策,禁止静默选边 |
| delete_local 枚举守卫 | `src/sync/sync-planner.js` | 枚举异常时拒绝按"远端已删除"删除本地文件,与 delete_remote 对称 |
| 死代码清理 | `src/sync/sync-planner.js` `_localState` | sha 不可用时文件消失按 `deleted` 处理(原分支永不可达) |

### 阶段 2(P1):决策闭环

| 修复 | 位置 | 说明 |
|---|---|---|
| 决策迁移 | `src/sync/conflict-service.js` `saveSet` | 新冲突集顶掉旧集前,旧集同路径的既有决策迁入新集,不再静默清空 |
| resolved 语义 | `conflict-service.js` `collectOverrides` + `src/sync/sync-controller.js` `resolveConflicts` | `resolved`(用户已手动编辑)映射为 keep_local:用户编辑后的本地内容即最新事实 |
| 决策验证轮 | `sync-controller.js` `_verifyResolution` + `SyncTrigger.VERIFY` | 决策执行成功后自动追加一轮验证同步;若再次冲突会重新暂停并呈现——"决策是否生效"始终可见 |

### 阶段 3(P2):鲁棒性

- `sync-engine.js`:M5 快照缺失改为中止(`LOCAL_CHANGED`,默认安全);`_runMerges` 签名对齐(消除第三参静默丢弃);`_assertRemoteMatchesLocal` 增加逐路径**内容 sha**比对(原只比存在性)。
- `src/sync/commit-builder.js`:批次预算统一为 base64 编码后口径(与单文件预检一致);删除条目按固定开销计入预算并允许独立成批。
- `src/git/github-provider.js`:owner/repo/分支名按路径段 URL 编码;compare 显式 `per_page=100`。
- `src/storage/sync-metadata-store.js`:schemaVersion 向前不兼容时拒绝按旧语义读取(`METADATA_VERSION_TOO_NEW`);"文件不存在"判定优先用错误码,文案匹配仅兜底。
- `src/sync/rebuild-service.js`:`inspect()` per-file 容错,单个损坏文档不再让整份重建预览失败,不可读文件显式列入 `unreadable`。
- `src/local/content-adapter.js`:front-matter 剥离正则容忍 BOM 与 CRLF/LF。
- `README.md`:协议标注更正为 LGPL-3.0(与 LICENSE 文件一致)。

## 四、第二轮补充(GitHub 实用性 + 日志体验,2026-09-05)

1. **限流不再被误判为权限不足**(`src/git/http-client.js`、`src/sync/retry-policy.js`、`src/sync/sync-error.js`):
   - GitHub 主速率限制以 403 返回,原逻辑只把 ≥500/429 标记可重试 → 批量首同步/多设备高频自动同步被限流后直接失败且不重试;
   - 新增 `RATE_LIMIT` 错误类别:按 `X-RateLimit-Remaining: 0`、`Retry-After` 头或正文 "rate limit" 文案识别,并从 `X-RateLimit-Reset`/`Retry-After` 提取建议等待时间;
   - 重试策略:限流不受"自动重试"开关约束,按服务端重置时间退避后**重新规划**,至多 2 次;单次等待超过 2 分钟转为可见失败(不挂起一小时),等下一轮自动同步自然恢复。
2. **下载大小预检 + 防盲写**(`src/sync/sync-engine.js`、`src/sync/sync-planner.js`):
   - 下载侧对称增加大小预检(目录树自带 size,零成本):超限文件跳过下载并计入 `skippedLargeDownloads`,不阻塞其余文件;
   - **修复盲写漏洞**:下载被跳过后,若下一轮把本地旧版本判为"本地修改"重新上传,会用未知新旧的本地内容盲写覆盖远端新版。现把超限路径传给规划器 `blockedDownloads`:凡涉及这些路径的自动上传/合并一律升级为人工冲突("远端文件超出大小上限,需人工处理");本地已删除(删除远端不需要读取内容)与双方无变化仍正常收敛;
   - `_applyLocalChanges` 保留跳过逻辑作为 apply 阶段的第二道防线(规划与 apply 之间远端漂移)。
3. **运行日志体验**(`src/ui/runtime-logs.js`):渲染改为**最新在前**(存储与容量淘汰逻辑不变),打开面板/实时刷新滚动停在顶部;级别标签中文化(`[信息]/[警告]/[错误]`)。
4. **README**:新增"已知限制"章节(权限位、大小上限、限流退避、重命名语义、Gitee 状态)。
5. 控制器同步完成日志补充 `大跳下`(跳过的超大下载)与 `漂移修`(canonical 修正)计数。

## 五、第三轮:冲突中心体验重构(`src/ui/conflict-dialog.js`)

用户反馈:多文件冲突时"一次只显示一个文件"、显示原始路径难以识别、排版不美观。

1. **根因(决策流程缺陷,非渲染 bug)**:原 `_flushIfAllDecided` 只要存在任意一条决策就关闭弹窗并触发重新规划 → 剩余未决策文件再次暂停 → 新冲突集顶掉旧集 → 弹窗重开,表现为"每次只蹦出一个文件"。
   **修复**:决策闸门改为"冲突集中**仍有待处理文件时不提交引擎**",弹窗保持打开逐个处理并显示进度(共 N · 已处理 M);全部决策完毕才收集 overrides 重新规划执行。「稍后处理」保留已做决策、不触发执行。
2. **友好名称**:显示 `笔记本名 / 文档标题`(内核 SQL 查询文档表 + lsNotebooks 解析),`.siyuan/conf.json` 显示为"笔记本配置(笔记本名)",assets 等显示"笔记本名 / 文件名";原始路径保留为小字副行,兼顾可识别性与可诊断性;内核不可用或查询失败时回退为路径 id,不阻塞弹窗。
3. **排版**:卡片式冲突列表(边框圆角)、标题加粗 + 状态徽标、原始路径与原因小字弱化、原因中内嵌的完整路径替换为"该文件"避免重复占行、批量决策栏与逐文件按钮分区、处理进度摘要行。
4. **测试**:新增决策闸门(3 文件逐个决策、全部完成才提交一次)与友好名称解析用例;全量 217/217 通过。

## 六、第四轮:重建"以本地为准"清不掉远端多出的笔记本(用户实证场景)

**现象**:网页端重建"以本地为准"(本地 2 个笔记本)报告成功;安卓端重建"以远程为准"后有 3 个笔记本;GitHub 上第三个笔记本始终存在;网页端事后普通同步也永远不出现它。

**根因(推理链,与全部症状吻合)**:网页端磁盘上残留了第三个笔记本的数据文件(`data/<id>/`),但该笔记本**不在内核笔记本列表**(UI 不显示)。重建与回读校验都以**磁盘扫描**为"本地全貌":
1. 重建规划:残留文件本地有、远端有、内容相同 → 判"未变化" → 不删除远端(远端清单里没有"多余"路径)→ 报告成功;
2. 回读校验:同一全貌 → 校验通过;
3. 重建提交树**包含**残留文件并写入 BASE → 之后普通同步一切"未变化" → 该笔记本成为"看不见的僵尸",下载不进来、删除不掉、修多少轮重建都没用。

此前两次修复(落地顺序、并发覆盖保护)针对的是其他环节,未触及"本地全貌"定义本身。

**修复**(`src/sync/sync-engine.js`、`src/sync/rebuild-service.js`、`src/plugin/index.js`):
1. 重建"以本地为准"时以**内核笔记本列表**为本地全貌:磁盘上 `data/<id>/` 不在列表内的路径视为残留 → 远端删除 + 本地清理(带备份),不参与上传;本地不清则下一轮普通同步会按"远端缺失的新文件"复活上传,所以两端必须同时清;
2. **安全边界**:`getNotebooks` 不可用/失败/为空时返回 null,不做残留清理,回退磁盘语义——宁可漏删不可误删;
3. 回读校验按清理后的本地全貌比对;`inspect()` 预览新增 `strayNotebookPaths`,重建确认弹窗显式列出"本地残留(不在笔记本列表)"的文件数与路径,用户确认前可见;
4. 测试:完整复刻用户场景(2 注册笔记本 + 1 磁盘残留笔记本)断言两端清理、收敛;另测列表不可得时不误删。

## 七、第五轮:conf.json 同步语义收窄 + 冲突中心名称显示修正

**用户反馈**:①`conf.json` 各端"莫名"变动,频繁产生冲突;②冲突中心显示的仍是 id 而非名称。

1. **conf.json 同步语义收窄**(新增 `src/local/notebook-conf.js`,接线 `sync-engine.js`/`sync-planner.js` 全链路):
   - 根因:思源内核会高频重写 `data/<id>/.siyuan/conf.json`(sort/closed 等设备状态各端自行变动),整文件比较与 M5 复查不断制造假修改与冲突;
   - **语义(按用户定义)**:规范化表示 = 仅含 `name`——**只有 name 以外的值(sort/closed 等)不同 → 视为文件一致**,不比较、不同步、不冲突;自动同步真正无感;
   - 上传 = 规范化内容(升级后首同步有一次迁移上传,此后远端恒为规范化形式);
   - 下载 = 字段级合并:名称取远端,sort/closed 等设备状态一律保留本地;本地缺失(新设备/重建)恢复远端全量;下载对 conf.json 跳过 M5 拦截(合并不具破坏性);
   - 规划器:conf.json 双侧都变时**不进文本 diff3 合并**(JSON 全文比对必冲突),改走下载的字段级合并,天然收敛;
   - 解析失败/无 name 的 conf.json 回退整文件语义,不丢数据。
2. **冲突中心名称显示修正**(`src/ui/conflict-dialog.js`):
   - 名称解析改为**分步刷新**:笔记本列表(快)先到先刷,不再被较慢的文档表查询拖累;
   - conf.json 等笔记本系统文件在笔记本名未知时不再显示无信息量的 id 括号(只显示"笔记本配置")。
3. **测试**:conf.json 语义全链路用例(迁移上传/本地设备字段漂移零操作/预升级远端迁移下载/改名+内核 touch 合并/收敛)+ 规范化与合并单元用例;全量 **222/222** 通过。

## 八、遗留事项与建议

- markdown 模式的根治方案仍是默认改 raw(本版本已通过回读校验保证收敛,但每轮多一次修正提交);建议观察 `canonical 修正` 日志频率,稳定后考虑默认值切换。
- 建议后续把 `_verifyResolution` 的验证轮结果接入同步历史面板,便于用户追溯"决策 → 验证"链路。
- 暂停门仍会拦截全部自动同步(单文件冲突 = 整体停摆),属于设计取舍,未在本轮改动。
